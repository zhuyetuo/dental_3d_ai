# 系统架构：前端、后端、算法服务、3D 渲染与交互、部署

模型怎么分工、数据怎么训练，见 [algorithm-architecture.md](algorithm-architecture.md)。这份文档讲系统怎么搭：每一层负责什么、怎么通信、怎么部署。

## 1. 总览

```
┌──────────────────────── 浏览器 ────────────────────────┐
│ React 页面：病例、上传、参数、报告                       │
│ Three.js 3D 引擎：加载 / 渲染 / 拾取 / 编辑              │
└───────────────┬────────────────────────────────────────┘
                │ HTTPS（REST；后续加 WebSocket 推送进度）
┌───────────────▼──────────────┐
│ frontend 容器：nginx          │  静态文件 + /api 反向代理
└───────────────┬──────────────┘
┌───────────────▼──────────────┐      ┌──────────────────────────┐
│ backend 容器：FastAPI         │─────▶│ 存储                       │
│ · 病例 / 文件 API             │      │ 现在：本地卷 /data          │
│ · 任务编排（流水线每一步）     │      │ 计划：PostgreSQL（元数据）  │
│ · 几何处理（dental_ai，CPU）  │      │      + MinIO/S3（网格文件） │
│ · 模型注册表（计划）          │      └──────────────────────────┘
└───────────────┬──────────────┘
                │ HTTP，按任务类型统一接口
┌───────────────▼──────────────────────────────────────────┐
│ 算法服务（GPU，每个模型一个容器）                           │
│ seg-tgnet（已有） · seg-sam2 · landmark · margin · crown-gen │
└──────────────────────────────────────────────────────────┘
```

三层的分工原则：
- **前端**只做显示和轻量交互（拾取、画笔、拖动），不做重计算；
- **后端**负责业务、编排和 CPU 几何计算；
- **算法服务**只做模型推理，无状态，可以独立扩容和替换。

## 2. 前端

### 2.1 技术栈

React 18 + TypeScript + Vite，3D 用 Three.js。生产环境由 nginx 托管静态文件。

### 2.2 3D 引擎模块

| 模块 | 职责 | 现状 |
|---|---|---|
| 加载 | 按扩展名选择 STL / PLY / OBJ 解析器；大文件用 Web Worker 解析，传输时用 Draco 压缩 | 解析器已完成；Worker 和 Draco 待做 |
| 渲染 | 按牙号逐顶点着色；牙颈线用线框显示；生成牙高亮；邻接 / 咬合距离热力图（自定义着色器）；透明度和显隐控制 | 着色、牙颈线、高亮已完成 |
| 拾取 | 射线求交，定位点击的牙齿、顶点；用 three-mesh-bvh 建 BVH 加速，几十万面的网格也能实时响应 | 已完成 |
| 编辑 | 改牙号（点击整颗牙）、画笔修改分割标签、牙位图选牙号 | 已完成（M2） |
| 颈缘线编辑 | 控制点拖动（射线落到网格上）、Shift+点击插入、Alt+点击删除；闭合 Catmull-Rom 样条逐点吸附到网格表面（BVH 最近点）；独立的撤销栈 | 已完成（M3） |
| 编辑（后续） | 套索；生成牙的移动 / 旋转 / 缩放（Gizmo） | 待做 |
| 撤销 / 重做 | 所有编辑操作记成命令（画笔一次拖动算一步），可撤销；保存时整份标签回传后端 | 已完成 |
| 测量 | 两点距离、缺隙宽度、邻接和咬合距离 | 待做 |

### 2.3 前后端的 3D 操作分工

| 操作 | 在哪做 | 原因 |
|---|---|---|
| 显示、拾取、画笔、拖动控制点 | 前端 | 需要实时响应 |
| 局部预览（比如拖动颈缘线时实时显示曲线） | 前端 | 只是显示 |
| 编辑确认后的重计算：封底、偏移、布尔运算、邻接 / 咬合调整 | 后端 | 计算量大、需要精确几何库，结果要可复现 |
| 模型推理 | 算法服务 | 需要 GPU |

前端编辑结果以**标签数组**或**控制点坐标**的形式提交给后端，由后端重新计算并返回新网格。这样同一套编辑记录就是训练数据（见算法架构中的数据回流）。

## 3. 后端

### 3.1 API（现有）

| 接口 | 说明 |
|---|---|
| `POST /api/cases` | 上传网格（可选：标签文件、对颌、设计参数 JSON），创建病例 |
| `GET /api/cases`、`GET /api/cases/{id}` | 病例列表 / 详情（状态、报告） |
| `POST /api/cases/{id}/run` | 提交处理任务 |
| `GET /api/cases/{id}/files/{path}` | 下载结果文件（分割 PLY、牙颈线 JSON、生成牙 STL） |

| `PUT /api/cases/{id}/prepared` | 设置预备体牙号（之后运行会为它们自动检测颈缘线） |
| `PUT /api/cases/{id}/margins` | 保存人工编辑的颈缘线（按版本；第一次修改前保存自动检测结果） |
| `PUT /api/cases/{id}/labels` | 保存人工修正的逐顶点标签（每次一个新版本；第一次修改前保存模型原始预测） |

计划增加：上下颌成对上传、批量上传（文件夹、最多 100 例）、提交编辑结果、按步骤重跑、ZIP 打包下载、用户和计费。

### 3.2 任务编排

现在（`backend/app/jobs.py`）：

- 设置了 `REDIS_URL`（docker-compose 默认设置）：处理任务进 **RQ + Redis** 队列，由单独的 `worker` 服务处理，API 进程不被重计算拖慢；`docker compose up --scale worker=3` 可以开多个 worker；
- 没设置：在 API 进程里用 FastAPI 的 BackgroundTasks 处理（本地开发、单机演示）；
- 病例文件通过共享卷（`DENTAL_DATA_DIR`）在 API 和 worker 之间共用，所以多个 worker 目前要在同一台机器上。

计划：

- 每个流水线步骤是一个任务，结果落盘，可以只重跑某一步（比如用户改了牙号，只重跑生成和封底）；
- 进度通过 WebSocket 推给前端；
- 批处理：一批病例拆成多个任务并行，按批次统计进度。

### 3.3 几何处理（CPU）

在后端进程（或单独的 CPU worker）里运行，代码在 `ml/dental_ai`：

- 已有：坐标系估计、缺牙检测、牙颈线提取、缺失牙镜像生成、底面封闭、碎片清理、编号检查；
- 计划：网格修复、偏移面（粘接间隙、最小厚度）、布尔运算（可用 manifold3d），碰撞和距离计算（用于邻接和咬合调整）。

### 3.4 模型注册表（计划）

记录每个算法服务的模型名、版本、训练数据版本、评估分数和接口地址。每个病例的报告里记下各步骤用了哪个模型的哪个版本，满足追溯要求。

## 4. 算法服务

- **一个模型一个容器**：各模型依赖的 PyTorch / CUDA 版本不同（TGNet 要 1.x + 自定义算子，新模型用 2.x），隔离后互不影响；
- **统一接口**：同类任务的接口相同。分割服务是 `POST /segment?jaw=upper|lower`，请求体是 OBJ，返回逐顶点 FDI 标签；后端通过环境变量 `SEGMENTER_URL` 切换；
- **无状态**：模型启动时加载一次；请求里带全部输入；方便多副本扩容；
- **健康检查**：`GET /health` 返回模型是否加载成功（比如权重缺失时给出原因）。

现有服务：`services/tgnet`（TGNet，PyTorch 1.13 + CUDA 11.6，pointops 按可配置的 GPU 架构编译）。

## 5. 数据约定

| 项 | 约定 |
|---|---|
| 单位 | 毫米 |
| 内部网格格式 | OBJ / PLY（保持顶点顺序，逐顶点标签依赖它）；STL 读入时合并顶点，不能和标签文件搭配 |
| 标签格式 | 与 Teeth3DS 一致：`{"jaw", "labels": [逐顶点 FDI，0 为牙龈], "instances"}` |
| 导出格式 | 封闭的 STL（给 CAM / 3D 打印） |
| 坐标系 | 内部估计牙弓坐标系（咬合方向、左右方向、正中矢状面）；分割服务的输入统一为 Teeth3DS 标准朝向（+Z 上方、+Y 后方、+X 患者左侧），后端调用前自动做朝向归一化（`orientation.py`，`SEGMENTER_ORIENT` 控制） |

## 6. 部署

### 6.1 现在：docker-compose 单机

```bash
docker compose up --build                  # 前端 + 后端
docker compose --profile gpu up --build    # 再加 TGNet（需要 NVIDIA GPU 和 nvidia-container-toolkit）
```

| 服务 | 镜像 | 端口 |
|---|---|---|
| frontend | node 构建 → nginx | 8080 |
| backend | python:3.12-slim + dental_ai（API） | 8000 |
| worker | 同 backend 镜像，`rq worker dental` | — |
| redis | redis:7-alpine（任务队列） | — |
| tgnet | pytorch 1.13.1-cuda11.6 + TGNet + pointops | 8001 |

病例数据存在 `case-data` 卷里（backend 和 worker 共用）；模型权重、模板库从 `models/` 目录只读挂载，示例病例从 `demo/` 挂载。
分割模型的选择顺序：`SEGMENTER_URL`（TGNet 服务）→ `DEEP_MODEL`（自己训练的深度模型）→ `BASELINE_MODEL`（CPU 基线）。

### 6.2 以后：多机 / 云

- 前端静态文件放 CDN；
- 后端多副本放在负载均衡后面，无状态（状态在数据库和对象存储里）。存储的迁移路径：`backend/app/storage.py` 现在是本地目录 + `case.json`，
  所有读写都经过 `case_path` / `load_case` / `save_case`；换成 PostgreSQL（病例元数据）+ S3 / MinIO（网格和结果文件）时，worker 处理前把输入拉到本地临时目录、处理后上传结果，API 读文件时返回对象存储的签名 URL，算法代码不用改；
- 任务队列的 worker 按队列长度扩容；
- GPU 服务单独放在 GPU 节点上，用 Kubernetes 按负载扩缩；
- 国内部署注意：医疗数据存储在境内，按等保要求配置。

## 7. 安全与合规

- 传输 HTTPS，存储加密；
- 账号、机构隔离，按角色控制权限（医生、技工、管理员）；
- 审计日志：谁在什么时候看了、改了哪个病例；
- 日志里不能出现患者信息；
- 模型版本、数据版本可追溯（医疗器械注册需要）。
